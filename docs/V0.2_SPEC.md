# Endpoint Doctor v0.2.x: Release-Facing Specification

## Authority and purpose

Endpoint Doctor diagnoses connectivity and protocol compatibility for an
OpenAI-compatible model API from the user's machine. It helps explain whether
a selected endpoint/model can complete specific diagnostic requests.

This document is the public release-facing specification for the frozen
v0.2 scope. It summarizes the project-level frozen engineering baseline;
it does not replace, expand, or redefine the product scope.

Endpoint Doctor **v0.2.0**, released on **2026-09-28**, established the initial
v0.2.x release baseline. Patch releases in the v0.2.x series may correct
packaging, documentation or defects without expanding the frozen v0.2 scope.

## Modes and compatibility

| Mode | Contract |
|---|---|
| Basic (default) | URL → DNS → TLS → HTTP → Authentication → /models; no inference request |
| Deep (`--deep --model ID`) | Basic → Chat → Streaming/SSE → Usage → Tool Calling → Structured Output |
| Legacy (`--chat --model ID`) | One non-streaming chat request; default `max_tokens=8`; legacy report/exit behavior retained |

Deep capability probes require an explicit nonempty model ID. Basic must pass
and the requested model must be found before Deep sends inference requests.
Usage is extracted from Chat/Streaming responses rather than run as a separate
probe. Deep requests can be billable; its tool round trip and conditional
Structured Output sub-test are explicit diagnostic steps, not hidden retries.
There are no automatic billable retries or fallback models.

The CLI retains exit codes 0 (pass), 1 (diagnostics did not pass, including
overall PARTIAL) and 2 (local usage/configuration error).

`--v2-json` is supported only for Basic/Deep. Legacy `--chat` uses human output
or `--json`; combining `--chat` with `--v2-json` is a usage error, even if
`--json` is also present. The CLI rejects this combination before reading the
API key or running diagnostics, with empty stdout, an explanatory stderr
message and exit code 2. It does not switch modes or send a diagnostic request.

## ProbeResult and report semantics

Each ProbeResult carries `name`, `status`, `support`, `summary`, `metrics`,
`evidence` and an optional `error_code`.

| Dimension | Values | Meaning |
|---|---|---|
| Execution status | PASS, FAIL, PARTIAL | Whether the probe satisfied its validation criteria |
| Capability support | SUPPORTED, UNSUPPORTED, UNKNOWN, NOT_APPLICABLE | What runtime evidence establishes about support or applicability |

FAIL and PARTIAL do not by themselves establish lack of support. UNKNOWN means
insufficient evidence, not UNSUPPORTED. Core failure makes the overall status
FAIL; a non-passing Streaming, Tool Calling or Structured Output probe makes it
PARTIAL when core checks pass.

Basic/Deep `--v2-json` emits `schema_version: "1"`, `apiwells_version`,
`overall_status` and ordered `probes`. Schema versioning is independent of
package versioning. Console and JSON reporters share aggregation and redaction.
Compatibility `--json` and legacy chat JSON remain available; see
[README](../README.md) for their distinct contracts.

Errors use a shared taxonomy for configuration, transport, authentication/HTTP,
JSON/schema, SSE/interruption and capability failures. Safe evidence explains
the observation without exposing raw sensitive exceptions.

## Capability validation

- **Chat:** validate a nonempty assistant text response and client total latency.
- **Streaming/SSE:** parse SSE, validate model-output events, track content/chunks
  and verify normal stream termination. Identify broken, incomplete and
  interrupted streams. TTFT is measured from request start to the first valid
  model-output event. HTTP headers, keepalive, role-only, empty and metadata-only
  events do not count. Total latency is distinct from TTFT and is measured by
  the client, not reported as server-only inference time.
- **Usage:** use provider-reported token counts only, never estimated values.
  Preserve missing fields as unavailable/null; do not calculate a missing total.
  Usage availability does not imply a model-quality or cost assessment.
- **Tool Calling:** require the full tool call → arguments JSON/schema validation
  → local diagnostic execution → tool result → second request → final response
  round trip. The final response must use the runtime tool result. Acceptance
  of a tools parameter or a first tool call alone cannot receive full PASS.
- **Structured Output:** request strict `json_schema`, parse the returned output
  and validate it against the JSON Schema. HTTP success or valid JSON alone is
  insufficient. An explicit unsupported rejection can cause one additional
  `json_object` sub-test; JSON-object-only success does not certify strict
  schema support. Request counts make these steps visible.

## Local execution and secret safety

The product is Local-First, with no telemetry by default and no hidden upload
of prompts, responses or usage. Diagnostic requests go to the user-selected
endpoint. API keys and Authorization header values must not be printed.
Centralized redaction applies to reports and safe error handling; raw provider
bodies are not dumped into reports.

HTTPS certificate verification remains enabled. Redirects, including same-host
redirects, are blocked to prevent credential forwarding. Environment proxies
require explicit opt-in. See [SECURITY.md](../SECURITY.md).

## Compatibility certification and release gates

The frozen certification gate requires at least three independent providers /
endpoints covering three to five Chinese models. Certification records must
identify provider, endpoint, model, date and tested
build, with per-capability status/support and sanitized runtime evidence.
Streaming requires SSE validation, Tool Calling requires the full round trip,
Structured Output requires JSON Schema validation, and Usage must be
provider-reported. A record may contain PARTIAL/UNKNOWN or FAIL/UNKNOWN without
establishing permanent lack of support. Not every provider supports every
capability.

ED-031 live validation is CLOSED / PASS. Preserve the existing matrix and all
three records linked in [COMPATIBILITY.md](COMPATIBILITY.md) as historical release
evidence. ED-032 Windows clean-install validation is CLOSED / PASS; it does not
replace ED-031 metrics. The final v0.2.0 release is **CLOSED / PASS**;
[RELEASE_CHECKLIST.md](RELEASE_CHECKLIST.md) records completed release acceptance,
the canonical source/tag and final artifact identities.

## Explicit non-goals

v0.2 does not include Benchmark, model scoring/ranking, recommendation, cost
optimization, Router, Gateway, long-term Monitoring, Web Dashboard, SaaS
accounts, cloud telemetry or complete Responses API coverage. Complete multimodal testing,
Agent Benchmark, complex enterprise administration and multi-region architecture
are also excluded.
